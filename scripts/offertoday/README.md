# OfferToday HK script adapter

Python standard library + existing `playwright-cli`; no model, copied login profile, Cookie export or browser Agent framework.

```sh
# Only when a connection is missing: explicitly attach ordinary Chrome via the official extension.
python3 scripts/offertoday/offertoday.py connect
# Reuse an existing connection; read loaded public jobs only.
python3 scripts/offertoday/offertoday.py discover
# Runner supplies the approved, private, RUNNING task bundle; do not invent a bundle or approval.
python3 scripts/offertoday/offertoday.py run /private/path/task.json
```

Connection metadata contains only `{session, workspace}` in ignored `.offertoday/connection.json` (0600). `OFFERTODAY_BROWSER_SESSION` / `OFFERTODAY_BROWSER_WORKDIR` override lookup. A metadata file may point to an already-attached workspace; no reattachment is needed for `discover/run`. Those commands never attach, log in or open a new browser. Missing/incompatible sessions stop. Shared Chrome is detached, not closed, when the overall operation ends.

Optional no-login search: set `OFFERTODAY_PUBLIC_PLAYWRIGHT_MODULE` to the existing absolute path to Playwright's `index.js` in the workbench process environment (requires local Node.js and Chrome). Only `read-candidates` for `/hk/search` and its subpaths uses a temporary Chrome. It needs no saved connection, closes only that new browser, and never falls back to an account after a challenge, timeout, redirect or unknown build. `/hk/recommend`, `discover`, and `run` still use the original connection. No change to HTTP requests, authorization, or the default configuration.

The observed `index.D4zvvLnm.js` build is supported for public reading: a canonical same-job URL, title, company, matching detail panel and visible availability cues bind the JD. The public `登入查看完整職位描述` prompt marks a preview as incomplete even when the preview is long. `available: null` is an explicit unknown, so an old JD retained for viewing cannot be used as current matching evidence. The continuation cursor is bound to the ordered list; if results change, the read stops rather than skipping a positional offset. The reader does not import chat bindings or click the application cue. Both native entry/locale pairs run through the sender contract with fully intercepted fixtures. The bundled sender currently refuses **both** at preflight, before the workbench records a claim: neither actual client has qualified native request, immutable attachment and per-action receipt bindings. Explicit manual application on the website is separate; anonymous reading does not enable sending.

## Execution contract

- HK single-job APPLICATION only, with a reviewed PDF/DOCX, exact initial text, contact/profile confirmation, and frozen hashes. Validation happens before browser access. Both published composers trim edge whitespace; a frozen message that would change is rejected for reapproval, not rewritten. Facts and résumé versions remain owned by the workbench; no profile auto-rewrite or translation.
- Discovery reads up to 40 currently loaded cards, using the public job-title/company links. It does not scroll, paginate, create tasks, or infer a missing full JD. Opaque job IDs retain case; queries do not distinguish jobs.
- Preflight navigates the existing tab to the approved job itself. Open dialogs and drafts are preserved rather than overwritten. It validates job/company or brand/recruiter, the native account, history baseline, attachment eligibility/capacity, and exact approved bytes. It never chooses a local file or sends anything.
- The driver recognizes the observed legacy (`index.BKzheqN_.js`, `lang-73AtwcZ1.js`) and newer (`index.D4zvvLnm.js`, `lang-DMtzyqWP.js`) pairs. The binding uses the matching root store; unknown builds and unqualified send bindings block. There is no guessed-export/default-store fallback. Job-card Chat/Apply buttons are not used because they can mutate state before opening a composer.
- To reuse an existing attachment, require the approved filename and eligible metadata, then read and hash the exact immutable version that can be dispatched before the first claim. Verify that same version during both send preparations. Ordinary downloads and preview files are not substitutes. With no matching file, a free attachment slot is required; old files/defaults are not deleted or changed. New file selection occurs only after the claim. The file input's native `input`/`change` events are suppressed during staging; the driver re-hashes an immutable copy and only then forwards one checked `change` in the still-bound account, job, conversation, build and dialog. Saving is guarded separately against the native pending upload key, filename, size and hash; an upload response alone does not authorize saving or show delivery.
- `SUBMITTING` must be HTTP-acknowledged before text send or file selection. Text uses `.js-message-input-editor`; the native résumé picker is identified by its résumé SVG, not the shared `open-resume` aria label alone. The approved résumé is explicitly selected; the previous default is not trusted.
- Text and résumé are separate sends. Each stage takes its own **direct server-history** baseline after the final attachment read and before the irreversible action. If history has changed before pressing Enter, stop without sending. `CONTACTED` requires a new own-text record matching the approved text and the same peer, and its callback must succeed before the attachment phase. `CV_DELIVERED` requires a different record in that conversation binding the exact immutable attachment version. The exact action must independently acknowledge a platform message ID before the driver can look for the corresponding history record. The verified history ID must equal that ID, be absent from its pre-send IDs and follow its history watermark (server sequence breaks timestamp ties); a résumé receipt must also follow the contact record. Matching text or attachment in history cannot supply the acknowledgement, even if it is the only match. This excludes previously seen identical text or an attachment already present between the two stages. The résumé button's non-sending actionability trial runs before sampling that stage's final history. After the sample, there is no second wait: the exact button must be enabled and pass the renderer hit-test, or the attempt stops. Window capture is an early filter only. A qualified adapter must enforce the same checks at the actual native upload, save, text and résumé handlers, and recheck after an async yield before an irreversible action. Check the actual native request as well as the live UI: job, account and peer must match, and the pending text must equal the approved text exactly, even when the editor already looks correct. For résumé sends, read and hash the original bytes by immutable version before sampling history. The live selection and actual native request must both carry that exact version; a matching ID, key, filename or size is not enough. The action acknowledgement and independent history must name the same version. No version-specific read or native request binding means no CV action. The transient check is removed on exit. In particular, a peer switch while the native button is waiting to become clickable stops the action and leaves the existing claim `UNKNOWN`.
- Check the exact editor contents when admitting the Enter event. Both published composers clear the editor before async transport, so at the dispatch boundary recheck the same native request, client ID, live account, peer, job and build instead of requiring the draft to still be visible.
- The text receipt checker requires original inbound `Sync_Message` bytes (`messageType=4`, `version=1`) from an independently qualified source. It decodes the exact native `clientMessageId` and platform `messageId` without JavaScript number rounding. A decoded object, malformed frame, mute indication, or unknown extension is not a receipt. Independent history must contain the same lossless message ID, and agree with the receipt's client ID and sequence when both report them. MQTT `PUBACK` and same-origin cross-tab events alone do not prove this source.
- DOM rows, local Loading/packet-send, editor clearing, upload/save success, or exit code zero are not receipts. A timeout, changed account/peer/page, failed callback, or missing history record retains `UNKNOWN`; no send is retried or restored. Unknown markup blocks instead of selecting another file or invoking AI.

The callback URL/token never enter browser JavaScript or website requests. Results contain only bounded task/receipt metadata, not message history, private profile values, file bytes or credentials. Platform-persisted résumé delivery is not a guarantee of employer reading, hiring outcome, or the native applied-history status.

## Verification boundary

Live navigation and discovery were checked. In a separately authorized single-job website pilot, the first-contact button sent a job card and default greeting; the custom text and chosen PDF each showed delivery in chat. Applied history independently showed contact and résumé sent, not a distinct application confirmation. The downloaded PDF from the sent card did not byte-match the source. The automated contract is still verified only in intercepted fixtures: the published résumé button on both builds sends an attachment ID without an explicit immutable revision and does not consume an acknowledgement ID. Neither build is qualified to send automatically. With no qualified send binding, preflight returns `NEEDS_INPUT` without navigating the shared tab.

The browser tests launch only random isolated fixture sessions and intercept **all** routes before fake OfferToday navigation. Both build fixtures POST text and CV to an independent loopback receiver that checks the actual payload, resolves immutable CV bytes, and returns distinct acknowledgements. History comes from a separate HTTP read; withholding it leaves `UNKNOWN` despite an acknowledgement. `fixtures/published-text-sync.json` records synthetic wire examples replayed through both actual published decoders and their shared `chat.CPHUXtPm.proto` schema offline. It records both the original frame and each decoder's output, including a large ID that rounded; it is not captured production traffic. Other fixture tests inject adversarial histories and state changes in the page. They never attach to `offertoday-current`, use user profiles, download real résumés or reach the real site.
