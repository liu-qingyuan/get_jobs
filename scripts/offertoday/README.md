# OfferToday HK script adapter

Python standard library + existing `playwright-cli`; no model, copied login profile, Cookie export or browser Agent framework.

```sh
# Only when a connection is missing: explicitly attach ordinary Chrome via the official extension.
python3 scripts/offertoday/offertoday.py connect
# Reuse an existing connection; read loaded public jobs only.
python3 scripts/offertoday/offertoday.py discover
# Runner supplies the approved, private, RUNNING task bundle; do not invent a bundle or approval.
python3 scripts/offertoday/offertoday.py run /private/path/task.json
```

Connection metadata contains only `{session, workspace}` in ignored `.offertoday/connection.json` (0600). `OFFERTODAY_BROWSER_SESSION` / `OFFERTODAY_BROWSER_WORKDIR` override lookup. A metadata file may point to an already-attached workspace; no reattachment is needed for `discover/run`. Those commands never attach, log in or open a new browser. Missing/incompatible sessions stop. Shared Chrome is detached, not closed, when the overall operation ends.

Optional no-login search: set `OFFERTODAY_PUBLIC_PLAYWRIGHT_MODULE` to the existing absolute path to Playwright's `index.js` in the workbench process environment (requires local Node.js and Chrome). Only `read-candidates` for `/hk/search` and its subpaths uses a temporary Chrome. It needs no saved connection, closes only that new browser, and never falls back to an account after a challenge, timeout, redirect or unknown build. `/hk/recommend`, `discover`, and `run` still use the original connection. No change to HTTP requests, authorization, or the default configuration.

The observed `index.D4zvvLnm.js` build is supported for public reading: a canonical same-job URL, title, company, matching detail panel and visible availability cues bind the JD. The public `登入查看完整職位描述` prompt marks a preview as incomplete even when the preview is long. `available: null` is an explicit unknown, so an old JD retained for viewing cannot be used as current matching evidence. The continuation cursor is bound to the ordered list; if results change, the read stops rather than skipping a positional offset. The reader does not import chat bindings or click the application cue. Both native entry/locale pairs run through the sender contract with fully intercepted fixtures. The bundled sender currently refuses **both** at preflight, before the workbench records a claim: neither actual client has qualified native request, input-to-native attachment ownership and per-action receipt bindings. The production send registry is empty; neither a flag nor a fixture grants production capability. Explicit manual application on the website is separate; anonymous reading does not enable sending.

## Execution contract

The authoritative converted-attachment **A** contract (#25/#30, also applicable to Boss) accepts platform conversion: approved local input hash → native attachment/account/job/conversation → this actual dispatch → a fresh CV delivery receipt. It does **not** prove recipient-side byte equality, reading, or native application status. A matching filename, attachment ID, upload success or history record alone is insufficient. Boss remains capability-blocked; this policy does not qualify its automatic greeting or sends.

Current implementation: the intercepted sender fixtures still exercise the older immutable-version checks, not converted-attachment A. No production binding implements A. The policy script also lacks the task owner's verified read-only JD/account/session context and exact stage-permission acknowledgement; hashes echoed from a bundle cannot fill that gap. Both production builds continue to stop before claim/effect.

- HK single-job APPLICATION only, with a reviewed PDF/DOCX input, exact initial text, contact/profile confirmation, and frozen input hashes. Validation happens before browser access. Both published composers trim edge whitespace; a frozen message that would change is rejected for reapproval, not rewritten. Facts and résumé versions remain owned by the workbench; no profile auto-rewrite or translation.
- Discovery reads up to 40 currently loaded cards, using the public job-title/company links. It does not scroll, paginate, create tasks, or infer a missing full JD. Opaque job IDs retain case; queries do not distinguish jobs.
- Preflight navigates the existing tab to the approved job itself. Open dialogs and drafts are preserved rather than overwritten. It validates job/company or brand/recruiter, the native account, history baseline, attachment eligibility/capacity, and exact approved bytes. It never chooses a local file or sends anything.
- The driver recognizes the observed legacy (`index.BKzheqN_.js`, `lang-73AtwcZ1.js`) and newer (`index.D4zvvLnm.js`, `lang-DMtzyqWP.js`) pairs. The binding uses the matching root store; unknown builds and unqualified send bindings block. There is no guessed-export/default-store fallback. Job-card Chat/Apply buttons are not used because they can mutate state before opening a composer.
- Before the first claim, check attachment provenance, eligibility/capacity and whether the qualified Adapter can prove A without effects. Existing attachments require a traceable link to the approved input, not a name/default match; ordinary downloads and previews do not establish that link. A platform copy need not byte-match the input. With no matching file, a free slot is required; old files/defaults are not deleted or changed. Newly selected local bytes must match the frozen hash; upload/save must preserve the traceable native attachment/account/job/conversation association.
- CONTACT and SEND_CV each require an exact acknowledged claim for the same task/attempt/stage, at most once each. Confirm and durably report CONTACTED before requesting SEND_CV; ambiguous contact stops. Selecting a file may immediately upload, so it requires the **CV** claim, not merely the earlier CONTACT claim. Text uses `.js-message-input-editor`; the native résumé picker is identified by its résumé SVG, not the shared `open-resume` aria label alone. Select the verified attachment explicitly; never trust a previous default.
- Text and résumé are separate sends. Each stage takes its own **direct server-history** baseline after final material/identity checks and before the irreversible action. If history changes before Enter, stop. CONTACTED requires a fresh own-text record matching the approved message and peer; it alone remains UNKNOWN. CV_DELIVERED requires a different, later record for the same attempt/job/conversation plus the complete A ownership chain. The actual dispatch must independently acknowledge a platform message ID before history can corroborate that exact ID. It must be absent from pre-send IDs and follow the history watermark (server sequence breaks timestamp ties); CV must also follow contact. Never choose a matching history ID as the acknowledgement. This excludes other tabs, old messages/receipts, and an identical attachment already present between stages. The résumé button's non-sending trial precedes the final history sample; afterwards the exact button must be enabled and pass the renderer hit-test without another wait. Window capture is only a prefilter: qualified native upload/save/text/CV handlers must recheck live job/account/peer/build and actual payload, including after async yields. The selected native attachment, actual dispatch, acknowledgement and independent history must share the verified input association; an immutable version is one possible proof, not a mandatory byte-equality requirement. Missing or changed associations stop the action, retain UNKNOWN after claim, and never authorize retry. Transient guards are released on exit.
- Check the exact editor contents when admitting the Enter event. Both published composers clear the editor before async transport, so at the dispatch boundary recheck the same native request, client ID, live account, peer, job and build instead of requiring the draft to still be visible.
- The text receipt checker requires original inbound `Sync_Message` bytes (`messageType=4`, `version=1`) from an independently qualified source. It decodes the exact native `clientMessageId` and platform `messageId` without JavaScript number rounding. A decoded object, malformed frame, mute indication, or unknown extension is not a receipt. Independent history must contain the same lossless message ID, and agree with the receipt's client ID and sequence when both report them. MQTT `PUBACK` and same-origin cross-tab events alone do not prove this source.
- DOM rows, local Loading/packet-send, editor clearing, upload/save success, or exit code zero are not receipts. A timeout, changed account/peer/page, failed callback, or missing history record retains `UNKNOWN`; no send is retried or restored. Unknown markup blocks instead of selecting another file or invoking AI.

The callback URL/token never enter browser JavaScript or website requests. Results contain only bounded task/receipt metadata, not message history, private profile values, file bytes or credentials. Platform-persisted résumé delivery is not a guarantee of employer reading, hiring outcome, or the native applied-history status.

## Verification boundary

Live navigation and discovery were checked. In a separately authorized single-job website pilot, the first-contact button sent a job card and default greeting; the custom text and chosen PDF each showed delivery in chat. Applied history independently showed contact and résumé sent, not a distinct application confirmation. The downloaded PDF from the sent card did not byte-match the source. The old immutable-version sender is verified only in intercepted fixtures, not as converted-attachment A. The published résumé buttons send an attachment ID without an explicit immutable revision and do not consume an acknowledgement ID; an absent revision is not itself a rejection under A, but the complete input/attachment/dispatch/receipt chain remains unverified. Neither build is qualified to send automatically. With no qualified send binding, preflight returns `NEEDS_INPUT` without navigating the shared tab (the existing callback representation for a proven no-effect capability stop). Real MATCH acceptance is pending lead/user; Pi workers do not send real messages/CVs.
